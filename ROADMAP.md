# Roadmap

Forward-looking scope for the workout tracker. Last updated 2026-05-02. Each entry notes whether an explicit design exists (→ `DECISIONS.md`) or it's just a recorded idea.

## Shipped — v3.2.0 (2026-05-03)

Live at www.sebvel.app as of `v3.2.0`. Per-user AI model selection — Coach, Plan flows, and Analyze each get an independent dropdown in the Coaching Profile screen, backed by a hardcoded allowlist mirrored on client (`js/models.js`) and server (`api/_models.js`).

- **Per-user AI model selection (`v3.2.0`).** New "AI models" section appended to the Coaching Profile form (hamburger → Coaching Profile). Three labelled `<select>` rows: Coach (default Haiku 4.5), Plan flows (default Sonnet 4.6, covers plan / refine / swap modes), Analyze (default Sonnet 4.6). Selections persist as `model_coach` / `model_plan` / `model_analyze` keys inside the existing `coaching_profile.data` JSONB blob — no schema migration. Each AI POST body now includes `model:` resolved via `coachingProfile.model_<bucket> || DEFAULT_MODELS[bucket]`. Server (`api/coach-chat`, `api/generate-plan`) reads the field, validates against `AVAILABLE_MODELS`, falls back to bucket default on miss with a `console.warn` so retired-model selections surface in Vercel logs. Operational pattern for new Anthropic releases: add a row to both `api/_models.js` and `js/models.js`, optionally retire an older entry, push — Vercel deploys client + API together. Spec + plan: [docs/superpowers/specs/2026-05-03-ai-model-selection-design.md](docs/superpowers/specs/2026-05-03-ai-model-selection-design.md), [docs/superpowers/plans/2026-05-03-ai-model-selection.md](docs/superpowers/plans/2026-05-03-ai-model-selection.md).

## Shipped — v3.1.0 (2026-05-02)

Live at www.sebvel.app as of `v3.1.0`. Per-workout weight-mode toggle — solves the "same exercise, different machine at different gyms" case (e.g., Hammer Strength Incline plate-loaded at gym A, cable-driven at gym B) without forcing a library-level edit.

- **Per-workout weight-mode toggle (`v3.1.0`).** Tappable chip on each exercise card next to "view recent" reads "Total" or "Per side" and toggles the `weight_mode` override for one workout placement. Editable in today's plan day, ad-hoc sessions, and the v3.0.3 historical-edit view; static label in read-only history detail. Hidden for bodyweight / none / cardio rows. New nullable `sets.weight_mode` column with check constraint `('total', 'per_side')`; NULL = inherit from `exercises.weight_mode` (default behavior — every existing row stays NULL after the migration). Two fan-out helpers (`setExerciseWeightMode` for editable today/ad-hoc, `historyUpdateExerciseWeightMode` for history-edit) keyed on `(workout_id, exercise_order)` mirror the existing `updateExerciseFanOut` / `historyUpdateExerciseRpe` pattern. Volume math (×2 for per-side), the "per side" hint, and CSV/JSON export all respect the override via a new `effectiveWeightMode(set, exerciseMeta)` resolver helper. New sets in a toggled placement inherit the override on `+ Add Set` / `+ Drop Set`. Two follow-on bug fixes during smoke testing: `createAdHocSession` / `deleteAdHocSession` no-plan-no-adhocs branch / `onEndPlan` no-ad-hoc branch now toggle `#emptyState` / `#summaryBar` (the six other lifecycle sites already did); chip click handlers fall back to a name/ID-based library lookup when `exerciseMeta` is null on plan-day prescribed rows (`stateFromWorkout` only attaches `exerciseMeta` for ad-hoc / extras). Spec + plan: [docs/superpowers/specs/2026-05-02-weight-mode-toggle-design.md](docs/superpowers/specs/2026-05-02-weight-mode-toggle-design.md), [docs/superpowers/plans/2026-05-02-weight-mode-toggle.md](docs/superpowers/plans/2026-05-02-weight-mode-toggle.md).

## Shipped — v3.0.x (2026-05-02)

Live at www.sebvel.app as of `v3.0.3`. The v3 line opens with the no-plan state becoming a first-class experience: the central workflow shifts from "you always have a plan loaded" to "you may have a plan loaded, but you may also be in a deliberate no-plan state without it feeling broken."

- **End plan + no-plan UX as first-class experience (`v3.0.0`).** Three motivating scenarios collapsed into one code path — mesocycle complete, pause/break, mistake recovery — all served by a single "End plan" affordance. Surfaces:
  - **Plans modal "End plan" button** on the active row (between Rename and Activate). Native confirm → `endActivePlan` flips `is_active = false`, clears plan-anchored in-memory state (`activePlanId` / `plan` / `todayState` / `todayPlanStates` / `historicalCache` / `daysWithHistory` / `exerciseIdCache` / `currentDay` / `suggestedDayIndex`), calls `refreshCoachForNewSession` so coach context drops the now-stale plan block, calls `clearHydrationSnapshot` so warm-boot lands on the empty state, defensively `stopTimerTick`s any running session interval. End is fully reversible via the existing `activateExistingPlan` — workouts, sets, and coach history are preserved across the round trip. No schema changes.
  - **Refreshed empty state.** The v1 "Tap Import to load your weekly plan JSON" relic is gone. `#emptyState` is now populated by `renderEmptyState` (ui.js) with three CTAs (Generate / Use a template / Blank session), a View full History link, and a Recent workouts list. `fetchRecentWorkouts(userId, 5)` returns the 5 most recent workouts (any `plan_id`, including ad-hoc) enriched with plan title + day name + location + done-set count; rows render as clickable bars and open via `openHistory()` + `openHistoryDetail(id)` so the back button lands sensibly on the History week view.
  - **Day-picker dropdown placeholder.** When `buildTabs` produces no plan-day or ad-hoc options, it renders a single disabled `<option>` reading "No active plan or session" instead of hiding the wrapper. UI chrome stays consistent.
  - **Start-screen overlay no longer forces the user.** Pre-v3 the overlay auto-opened on hydrate's no-plan branch and after `onEndPlan`, with the close button hidden when there was nowhere to fall back to. Now the empty state IS the fallback, so the overlay does not auto-open on End / no-plan-hydrate, and its close button is always available. Manual entry via the empty-state Template CTA or hamburger → Start a workout still works.
  - **No-plan hydrate loads the exercise library.** Pre-v3, `hydrate`'s no-plan branch returned early without loading `exerciseLibraryById`, so `stateFromWorkout` resolved `exerciseMeta` to null and `renderHistoryDetail` fell back to the literal "Exercise" string for every card — visible when tapping a Recent workouts row in no-plan state. The branch now `await`s `loadExerciseLibrary()` and fires `loadLocations()` in the background so History detail resolves names + gym tags correctly.
  - **Spec + plan:** [docs/superpowers/specs/2026-05-02-end-plan-and-no-plan-ux-design.md](docs/superpowers/specs/2026-05-02-end-plan-and-no-plan-ux-design.md), [docs/superpowers/plans/2026-05-02-end-plan-and-no-plan-ux.md](docs/superpowers/plans/2026-05-02-end-plan-and-no-plan-ux.md).
- **No-plan hydrate loads + focuses today's ad-hocs (`v3.0.1`).** Closes the only follow-up flagged in v3.0.0. Pre-v3.0.1 the no-plan branch only loaded the library + locations; `todayAdHocs` was left empty, so a user with an in-progress ad-hoc workout in no-plan state saw the empty state on hard reload (the workout row was preserved in the DB but invisible in the UI). Now the branch parallel-loads today's ad-hoc workouts (filtered to `plan_id IS NULL` within `sessionBounds`) alongside the library + locations, populates `todayAdHocs` via `stateFromWorkout`, and applies a focus hierarchy (in-progress wins; else first ad-hoc of any state; else empty state). When focused: hide empty state, show summary bar, run `buildTabs` + `buildDay` so the ad-hoc card renders.
- **Auto-open start-screen in no-plan + ad-hoc state (`v3.0.2`).** When the user lands in the no-plan branch with an ad-hoc focused (either on hydrate after reload, or after `onEndPlan` with an ad-hoc going), also auto-opens the start-screen overlay so no-plan options (Generate / Use a template / Blank session) are surfaced alongside the focused session. Close button is always visible in the no-plan branch (per the v3.0.0 fix), so this is a gentle prompt rather than a forced wall. `onEndPlan` also gains the focus hierarchy that hydrate uses: in-progress ad-hoc wins, else first ad-hoc of any state, else fall through to the empty state. Pre-v3.0.2 `onEndPlan` always rendered the empty state regardless of remaining ad-hocs.
- **Edit historical workouts without restarting (`v3.0.3`).** Pre-v3.0.3 the only ways to change a logged workout were Bring to today (which moves the whole session to today and resets the timer) or Discard session. Neither covered "I forgot to type the weight on set 2 / forgot to mark RPE / want to add a session note after the fact." Adds an Edit toggle to the history-detail header that flips the whole detail into editable mode: set inputs (weight/reps; or duration/distance for cardio rows), per-set done check, per-exercise RPE, per-exercise note, workout-level session notes — all auto-save on change, no Save button. New `historyEditMode` flag (resets on close/back). Five new persistence helpers in `data.js`: `historyUpdateSetField`, `historyUpdateSetDone`, `historyUpdateExerciseRpe`, `historyUpdateExerciseNote`, `historyUpdateWorkoutNotes`. Per-exercise RPE + note updates fan out to all sets in the exercise. Drop-set cascade intentionally NOT applied in history edit (each row toggles independently). Out of scope (handled by Bring to today): add/delete sets, swap exercise, drag-to-reorder, exercise-level delete.

## Shipped — v2.5.x (2026-04-23 → 2026-05-01)

Live at www.sebvel.app as of `v2.5.12`. The v2.5 line covered four major feature families: adaptive coaching profile, iterative plan refinement, cardio Phase 1, and drop sets Phase 1.

- **Adaptive coaching profile (`v2.5.0` – `v2.5.1`).** New `coaching_profile` table (jsonb data column, owner-only RLS) replaces the hardcoded CLIENT PROFILE / Injury / Phase blocks in `system-prompt-core.md`. Editable via a "Coaching Profile" screen in the hamburger menu (sex, height, weight, experience, environment, split preference, goal, phase, injuries-as-list, special instructions). All four Claude call paths (plan, analyze, swap, coach-chat) read the profile via service-role on every call and inject a `CLIENT PROFILE` block at the top of the user message. Replaces the v2.5 layer 1 ROADMAP entry.
- **Analyze-time profile updates / Option C (`v2.5.2`).** Closes layer 3 of the adaptive coaching profile (originally planned as a separate "periodic prompt self-revision" pass). Analyze mode's response now carries an optional `profile_updates: [...]` array; the review UI renders each as a diff card with a per-field accept checkbox. "Apply selected" merges accepted changes into `coaching_profile` via `applyProfileUpdatesFrom` (data.js) + `saveCoachingProfile`. Field allowlist enforced server-side (sex / height / experience are off-limits — client-owned). Layer 2 (AI-generated behavioral observations) remains the only piece of the original three-layer plan still open.
- **Iterative plan refinement (`v2.5.3` – `v2.5.4`).** Plan-gen review screen gains a "What would you change?" textarea + Refine button below the day cards. Clicking fires `/api/generate-plan` with `mode: 'refine'`, sending `current_plan` + `iteration_history` (prior `{plan, feedback}` pairs) + the new feedback. Server reconstructs the multi-turn conversation, replays prior turns, and adds `cache_control` on the latest assistant turn so iter N+1 reuses iter N's emission as cached prefix (~$0.01-0.02/iteration warm). Response is `{ plan, change_notes }`; the review re-renders the revised plan with a "WHAT CHANGED" banner and meta line bumps to "revision N". v2.5.4 fixed a validation bug rejecting day-count changes.
- **Hydrate parallelization + deferred loads (`v2.5.5`).** Pre-v2.5.5 hydrate awaited five Supabase queries serially after the plan loaded; aggregate critical path was ~6× the slowest query. Now Phase 1 awaits today's workouts + library + days-with-history in parallel; locations / suggested-day-index / recent-exercises / focused-day historical defer to Phase 2 (background) with re-render-on-arrival for affected surfaces. Net cold-cache hydrate latency dropped from ~1-2s to ~600-1000ms (now bound by max(query times)).
- **Start-screen Generate path (`v2.5.6`).** Start-screen modal gains a "Generate a new plan" card alongside Suggested-day / Pick-a-day / Use-a-template / Blank. Promoted to primary styling on the no-plan empty-state path; demoted to standard styling when there's an active plan. Click closes the start screen and opens the existing Generate flow. No new endpoints — pure UI shortcut.
- **Cardio Phase 1 (`v2.5.7` – `v2.5.8`).** Two new nullable columns on `sets` (`duration_seconds`, `distance`) + 5 new seed exercises (sprint intervals, sled push conditioning, farmer's walk conditioning, ski erg, versa climber) + battle rope reclassed `muscle_group='cardio'`. Set row branches via `isCardioExerciseName(name)` library lookup: cardio rows render DURATION (mm:ss text input) + DIST (numeric, miles) instead of weight + reps. View Recent / History detail render cardio rows in the new format ("30:00 · 0.5mi"). System-prompt-plan.md gains a CARDIO PRESCRIPTION section (duration-based sets, phase-aware dosing 2-3× LISS in bulk vs 4-5× with HIIT in cut). Coach chat also gets a Cardio decisions line. Phase 2 (heart rate, first-class intervals, weekly cardio volume tracking) deferred.
- **Rest timer floating pill (`v2.5.9`).** Rest timer was a centered modal with a 50% backdrop overlay that blocked the whole app during rest. Rewritten as a compact horizontal pill at bottom-center (~280px × 44px, z-index 200): `[-15s] [1:30] [+15s] [Skip]`. Backdrop overlay forced `display: none`; the rest of the app stays interactive while resting. Completion chime + vibrate + auto-dismiss + visibilitychange catch-up unchanged.
- **+ Add Set carry-forward (`v2.5.10`).** Tap + Add Set after a 100×12 set → new set pre-fills with 100 weight + 12 reps. Cardio path carries duration + distance instead. Most-recent-first scan, first populated set wins. New set still has `done=false` so the user has to tap done — auto-fill, not auto-completion. Applies to extras on prescribed exercises and ad-hoc / extras-as-cards sessions.
- **Drop sets Phase 1 (`v2.5.11` – `v2.5.12`).** Schema additions to `sets`: `set_type text default 'standard' check in ('standard','drop','superset','giant')` + `parent_set_id uuid references sets(id) on delete cascade` + partial index. UI: + Drop Set button per editable exercise (hidden on cardio); drop entries render with `→` label, indented + accent left-border. Cascade-on-parent-done: marking a parent done auto-marks all `setType='drop' AND parentSetIdx===si` children done with the same `completed_at`; rest timer fires once after the cascade completes. AI plan integration uses a flat format (`set_type: 'drop'` field on individual set entries) rather than nested `drop_sets` arrays — keeps `plan.sets[]` and in-memory `exState.sets[]` aligned at the same index. Prescribed drops auto-render in the review and during the session; cascade auto-fills each child's prescribed weight/reps from `plan.sets[ci]`. Supersets / giant sets share the schema but defer to Phase 3 — different UI (cross-exercise pairing) and AI format.

## Shipped — v2.4.x (2026-04-21 → 2026-04-22)

Live at www.sebvel.app as of `v2.4.22`. v2.4 spans the hydration cache, session lifecycle hardening, persistent coach history (3 parts), and a fairly large set of UX hardening fixes.

- **Hydration cache for fast warm boot (`v2.4.0`).** localStorage-backed snapshot of the last-painted tracker state (`wt.hydration.v1`, schema-versioned, 7d max age). Painted synchronously on cold-paint via `paintFromCache()` IIFE in `app.js` BEFORE any network call — running session timer + logged sets visible at 0ms on warm boot. `hydrate()` reconciles in the background, swapping in fresh server state. "Refreshing…" pill in the header signals the optimistic-paint state. Saved on `visibilitychange → hidden`, `beforeunload`, plan activation, and successful hydrate end. Cleared on sign-out + on user-id mismatch. Schema-versioned with age-gating; `HYDRATION_SCHEMA_VERSION` bumps on cache-shape changes.
- **Stale today-state filter (`v2.4.17`).** `paintFromCache` was restoring yesterday's `todayPlanStates` from cache, occasionally shadowing earlier-this-week historical workouts on the day-tab. Now gates the today-state restore on `savedAt >= today's local midnight` — yesterday's snapshot only restores plan / title / day-tabs (the structural bits); today-state comes fresh from hydrate.
- **Resume-session prompt on add-while-ended (`v2.4.18`).** Adding a set, adding an exercise, or checking a set done while a session is `endedAt`-marked now opens a one-shot modal: "This session ended at HH:MM. Resume the timer so this counts toward your session duration?" Three options: Resume timer (calls `resumeSession` then runs the action), Just log it (sets a per-session suppress flag so the prompt doesn't re-fire), Cancel. Suppress flag clears on explicit Resume.
- **Persistent coach chat history — Part A (`v2.4.19`).** New `coach_messages` table (role, content, context_type, exercise_name, created_at) + RLS. Frontend writes durable rows on every coaching surface: chat sends, swap accept, plan-gen accept, analyze response. Replaces the prior in-memory `chatHistory` ring buffer (still kept for the live-conversation thread) — the durable log survives sign-out / session start / plan save and powers cross-session continuity in Claude prompts.
- **Coach history injection — Part B (`v2.4.20`).** All four Claude call paths (plan, analyze, swap, coach-chat) now query `coach_messages` (last 2 weeks + current week, Sun-anchored) and inject a "RECENT COACHING CONVERSATIONS" block into the user message. New `COACHING CONTINUITY` directive in `system-prompt-core.md` + inline coach-chat / swap prompts tell Claude to honor prior advice, track injury evolution, respect swap decisions, and reference past conversations naturally. coach-chat endpoint gets `SUPABASE_SERVICE_ROLE_KEY` for the side-channel query.
- **Coach panel history view — Part C (`v2.4.21`).** Coach chat panel now loads + displays the last 2 weeks of coach_messages on open. Date headers (`— Tue, Apr 22 —`), past-session messages rendered at 0.65 opacity (.coach-msg.history), context badges for swap/plan_generation rows. Empty state shows the welcome message; cap silently at most-recent 50; 5-minute cache so rapid open/close doesn't re-query.
- **Single-outcome rows (`v2.4.22`).** Replaced the verbose multi-row coach-message logging (request / suggestion / retry / accept on swap; submit row on plan-gen carrying full analyze paste) with one `Accepted swap: X → Y (reason: Z). Coach's rationale: <note>` row per accepted swap and one `Accepted plan: <title>. Weeks: N. Notes: <capped 200>` per accepted plan. Cancelled / rejected outcomes leave no trace. Resolves Problem 1 (rejected generations polluting context) and Problem 2 (analyze-text duplication when plan-gen submit logged the full notes field).
- **v2.4.x hardening grab-bag.** Across v2.4.1-v2.4.16: ad-hoc dedup on hydrate (v2.4.16 fix preventing 23505 on persistSet from duplicate findAdHoc matches), template-mid-session add path, ad-hoc reorder fix, auto-rest-timer (v2.4.14), surface persistSet error on toast (v2.4.15), Plans-modal rename (v2.4.12), Fitbod cable-woodchop data recovery + seed-library completeness fix (v2.4.1), and several smaller bug fixes. Each commit message has the diagnosis.

## Infrastructure / scaling

- **GitHub Actions warmup workflow — two layers.** The `vercel.json` cron at `0 9 * * *` is **decorative** in practice: Vercel Hobby caps crons at once-per-day, and by the time the user actually opens the app (not at 5am EDT), the Fluid Compute instance has recycled and the Anthropic cache has expired (1h TTL). Two targeted upgrades, both deferred until cold-start pain is measurable:
  - **(a) Replace the Vercel cron with a GitHub Actions workflow pinging `?warmup=true`** on every ~10 min. Free for public repos; for a private repo, scope the schedule to 6am-11pm local to stay under the 2000-min/mo free budget. Fifteen-line YAML file. Only warms the Fluid Compute instance (the `?warmup=true` branch returns early without touching Anthropic), so this buys ~500-1500ms of saved JS/module cold-start time per call. Known gotcha: GitHub Actions schedules can be delayed 15-30 min under load — fine for our use case but not guaranteed timing.
  - **(b) Keep the Anthropic prompt cache warm too (huge maybe).** Modify the warmup handler to make a minimal Anthropic call on the warmup path — same cached system prompt, trivial user message, `max_tokens: 10`. This actually keeps the 1h Anthropic TTL refreshed. Estimated cost at every-50-min cadence: ~$3/mo of extra input tokens (cache hits are ~$0.003/call). Only worth doing if the ~30-35s cold-start Anthropic cache-miss is genuinely painful — the v2.0.26 silent-retry already hides it for plan-gen, and analyze is rare enough that paying the miss once per session is tolerable. Per-mode: the Anthropic cache is per-system-prompt-prefix, so warming only helps the mode the warmup call uses — would need two warmup variants to keep both plan-gen and analyze caches hot.
  - Both layers supersede the current Vercel cron, which would be removed from `vercel.json` once GH Actions takes over. Pro upgrade ($20/mo) is an alternative to both but costs 6-7x more than the GH Actions + ~$3 Anthropic cost with less flexibility.
- **Vercel Pro upgrade ($20/mo).** Function timeout goes from 60s to 300s. Would eliminate the 55s timeout concern entirely and open space for multi-week periodization, streaming, bigger output windows. Low-priority as long as Sonnet + 1h cache stays within 30s typical.
- **Anthropic SDK swap.** Currently using raw `fetch` in `api/generate-plan.js` for zero-dep deployment. Could swap to `@anthropic-ai/sdk` for typed responses, retry handling, streaming support. Only worth it if we move to chat/streaming UX.
- **System prompt admin UI.** Currently edit `system-prompt.md` + commit + redeploy. If prompt iteration becomes frequent, a Supabase-backed prompt row + hamburger-menu editor would let the user tweak without a deploy loop. Deferred per DECISIONS.md — current flow is fine for weekly iteration cadence.

The new Plans modal already lets the user re-activate the old plan as a workaround; a cleaner UX would surface the orphaned sessions inline.

- **Plan editing in-app.** Listed as a non-goal; the edit surface is accept/regenerate/import. Could add inline weight/rep overrides on individual exercises if the AI gets something wrong and the user wants to adjust without a full regenerate.

## Known limitations to fix

- **`updateExerciseFanOut` is missing the `user_id` filter** that `setExerciseWeightMode` and the `historyUpdate*` helpers all include. RLS still blocks cross-user writes, but the in-process defense-in-depth is asymmetric. One-line fix: add `.eq('user_id', userId)` to the UPDATE chain at `js/data.js` (around the rpe + note fan-out at the top of `updateExerciseFanOut`). Surfaced during the v3.1.0 code review.
- **`20260502010000_set_weight_mode_override.sql` uses an unnamed inline check constraint** while the immediately-preceding migration `20260501010000_drop_sets.sql` named its constraint (`sets_set_type_check`). Style drift only — no behavioral difference. To fix, replace the inline `check (...)` with a named `add constraint sets_weight_mode_check check (...)`. Probably wants to live in a follow-up migration that drops the unnamed and adds the named, since editing applied migrations is forbidden.
- **Five inline `(sl.weight_mode || weightMode)` sites in `js/ui.js` could use `effectiveWeightMode` for style uniformity.** Functionally equivalent because `weightMode` is the placement-level effective mode passed in. Sites are inside `renderSetRow` callers (~628, 643, 737, 849, 2242). The plan called for the helper at every site; these slipped through. Sweep is mechanical.
- **Race window between `setExerciseWeightMode` and `persistSet` for the same placement.** `setExerciseWeightMode` mirrors in-memory only AFTER the DB UPDATE resolves (~50-200ms round-trip). If a `persistSet` fires for the same placement during that await, its `buildSetPayload` will read the stale `sl.weight_mode = null` and write it back, undoing the just-stamped value on one row. Realistic only if the user taps the chip and immediately types a value before the round-trip resolves. Fix: mirror in-memory BEFORE the await (optimistic), and revert on error. Same pattern other persistence paths in this app already use.
